这三个词经常被混用，但我倾向于划出一条清晰的边界——因为边界背后是责任划分：**哪一层为失败负责**。

## 三个词各自的职责

**Scaffold** 是围绕单次模型调用搭的脚手架：提示模板、输出解析、失败重试。它假设模型一次调用就能完成任务，关心的是「这一次调用如何更稳」。

**Harness** 是让模型在长程任务里安全行动的执行环境：状态外部化、工具白名单、验证门禁、运行回执。它假设模型会跑很多步、会犯错、上下文会被冲刷，关心的是「几十步之后，系统如何仍然可信」。

**Agent Runtime** 则是更进一步的运行时假设：调度、生命周期、跨会话记忆全部由平台托管。开发者描述意图，运行时负责执行——这是平台厂的终局想象，不是应用开发者今天能依赖的东西。

| | Scaffold | Harness | Runtime |
| --- | --- | --- | --- |
| 时间跨度 | 单次调用 | 长程任务 | 跨会话 / 常驻 |
| 状态 | 无（靠上下文） | 外部化（文件 / DB） | 平台托管 |
| 失败处理 | 重试 | 门禁 + 回执 + 可恢复 | 运行时调度 |
| 典型产物 | Prompt 模板 | 清单、DAG、台账 | Agent 平台 |

## 判断标准：谁为失败负责

我的判断标准很简单：**失败发生时，是「你的 prompt 问题」还是「系统可捕获、可重放的事件」？**

Scaffold 里，失败归因于提示词写得不好；Harness 里，失败应当是系统记录在案的证据——这也是为什么我在数模 Harness 里坚持 run receipt（stdout / stderr / exit code 全保留）：失败不是异常，是证据。

## 常见错误：用 Scaffold 思路做 Harness 的事

实践里最容易犯的错，是加一段系统提示词，指望模型「记得」规则。长程任务里上下文会被冲刷，写在 prompt 里的承诺会随轮数稀释。

规则必须落在模型之外：门禁、台账、工件 DAG。在 ProjectMemo 里对应的是「LLM 只做结构化节点，写入与校验收在应用层」；在数模 Harness 里对应的是「手改 Markdown 投影不让 Gate 通过，必须改源头重新投影」。共同点只有一个——**不信任上下文的持久性**。

## 边界清楚了，选型也就清楚了

- 快速验证想法 → Scaffold 足够，别过度设计；
- 要交付可靠行动 → 先设计 Harness，把状态和门禁想清楚；
- 调度与记忆复杂到自研不经济 → 再考虑 Runtime。

长程可靠性，八成是工程问题，两成才是模型问题——这是我把重心放在 Harness 而不是 prompt 的原因。
